## 2. Поток приглашения

### 2.1. Существующий пользователь (уже зарегистрирован)

```
[ADMIN] → Создаёт приглашение (email, роль) → [Бэкенд] → invitations + токен
                                                              ↓
[Email] → Письмо со ссылкой /invite/{token} → [Пользователь]
                                                              ↓
Пользователь переходит по ссылке
                                                              ↓
┌─────────────────────────────────────────────────────────────────────────┐
│ Бэкенд: GET /public/invitations/{token}                                  │
│   • Проверка: токен существует, PENDING, не истёк                       │
│   • userExists: true (email найден в users)                              │
│   • isAuthenticated: true/false                                           │
└─────────────────────────────────────────────────────────────────────────┘
                                                              ↓
        ┌───────────────────────┬───────────────────────────────┐
        │ Аутентифицирован      │ Не аутентифицирован           │
        │ (текущий user.email   │                               │
        │  == inv.email)        │                               │
        ↓                       ↓                               │
  POST /accept                 Редирект на /login?email=...     │
  → Добавить в workspace       &inviteToken=...                 │
  → ACCEPTED                   После логина: автоматически     │
  → Редирект в workspace       принять приглашение              │
```

### 2.2. Новый пользователь (ещё не зарегистрирован)

```
[ADMIN] → Создаёт приглашение → [Бэкенд] → invitations + токен
                                              ↓
[Email] → Письмо со ссылкой → [Пользователь]
                                              ↓
Пользователь переходит по ссылке
                                              ↓
┌─────────────────────────────────────────────────────────────────────────┐
│ Бэкенд: GET /public/invitations/{token}                                  │
│   • userExists: false (email не найден в users)                           │
│   • isAuthenticated: false (или true, но email другой — см. раздел 3)     │
└─────────────────────────────────────────────────────────────────────────┘
                                              ↓
  Редирект на /register?email=...&inviteToken=...
  (email pre-filled, нельзя менять)
                                              ↓
  После успешной регистрации:
  • Создать user
  • Добавить в workspace с ролями из приглашения
  • inv.status = ACCEPTED
  • Редирект в workspace
```

### 2.3. Сводка сценариев

| userExists | isAuthenticated | email совпадает | Действие |
|------------|-----------------|-----------------|----------|
| true | true | да | Сразу принять, редирект в workspace |
| true | true | нет | Ошибка: приглашение на другой email (раздел 3) |
| true | false | — | Редирект на /login, после логина принять |
| false | false | — | Редирект на /register с pre-filled email |
| false | true | нет | Ошибка: приглашение на другой email |

## 3. Защита от приглашения не того человека

### 3.1. Проблема

- ADMIN вводит `ivan@company.com`, но имел в виду `ivan.petrov@company.com`
- Письмо уходит на `ivan@company.com` — другой человек получает доступ в workspace
- Или: пользователь вошёл под `alice@mail.ru`, а приглашение на `alice@company.com` — разные аккаунты

### 3.2. Меры защиты

#### A. Жёсткая привязка email к токену

- Токен привязан к конкретному `email` в `invitations`
- При принятии: `currentUser.Email` **должен совпадать** с `invitation.email`
- Если не совпадает → `400 Bad Request: "Invitation is for different email. Please log in as {invitation.email}"`

#### B. Нельзя менять email при регистрации по invite

- На странице `/register?email=...&inviteToken=...` поле email **readonly** или скрыто
- Пользователь не может зарегистрироваться с другим email и «украсть» приглашение

#### C. Подтверждение email при регистрации (опционально)

- После регистрации отправить verification email
- До верификации — ограниченный доступ (например, только просмотр)
- Снижает риск, если кто-то ввёл чужой email по ошибке: владелец почты увидит письмо и поймёт, что его пригласили по ошибке

#### D. Двойное подтверждение при создании приглашения (опционально)

- Показать ADMIN: «Вы приглашаете ivan@company.com. Подтвердите email»
- Кнопка «Отправить» только после явного подтверждения

#### E. Отзыв приглашения

- ADMIN может отозвать приглашение до принятия
- Если ошибка обнаружена быстро — `DELETE /invitations/{id}` → статус CANCELLED

#### F. Ограниченный срок действия

- `expires_at` (например, 7 дней) — снижает окно, когда ошибочная ссылка активна

### 3.3. Рекомендуемый минимум

- **Обязательно**: A, B, E, F
- **Желательно**: C (verification) при масштабировании
- **По необходимости**: D для чувствительных workspace

## 4. Email-рассылки: варианты реализации

### 4.1. Интерфейс

```go
type EmailService interface {
    SendInviteEmail(to, inviteLink, workspaceName, invitedByName string) error
    // Позже: SendVerificationEmail, SendPasswordReset, etc.
}
```

### 4.2. Варианты провайдеров

| Провайдер | Плюсы | Минусы | Когда использовать |
|-----------|-------|--------|---------------------|
| **SendGrid** | Простой API, бесплатный tier (100 писем/день), шаблоны | Лимиты на бесплатном | Стартапы, MVP |
| **AWS SES** | Дёшево, масштабируемо, интеграция с AWS | Нужен AWS аккаунт, настройка домена | Продакшн, большие объёмы |
| **Resend** | Современный API, React Email шаблоны | Молодой сервис | Современный стек |
| **SMTP (свой сервер)** | Полный контроль | Спам-фильтры, доставка, поддержка | Корпоративная почта |
| **Mailgun** | Надёжность, аналитика | Платный | Средний/крупный бизнес |

### 4.3. Рекомендации по выбору

1. **Разработка / staging**: заглушка — логировать в консоль или писать в файл. Не отправлять реальные письма.
2. **MVP / малый трафик**: SendGrid или Resend — быстрый старт.
3. **Продакшн, рост**: AWS SES — низкая цена при масштабе.
4. **Корпоративный домен**: SMTP через корпоративный сервер, если политика безопасности требует.

### 4.4. Архитектура отправки

```
[API] → [EmailService] → [Провайдер API / SMTP]
                ↓
        Очередь (опционально)
        • RabbitMQ, Redis, AWS SQS
        • Асинхронная отправка, retry при ошибках
```

**Синхронно** (простой вариант):
- `CreateInvitation` → сохранить в БД → вызвать `EmailService.SendInviteEmail` → вернуть ответ
- Минус: задержка ответа при медленной доставке

**Асинхронно** (рекомендуется для продакшн):
- `CreateInvitation` → сохранить в БД → положить задачу в очередь → вернуть ответ
- Воркер забирает задачу и отправляет письмо
- Retry при временных ошибках (5xx, таймаут)

### 4.5. Шаблон письма

- HTML + plain text fallback
- Переменные: `{{inviteLink}}`, `{{workspaceName}}`, `{{invitedByName}}`, `{{expiresAt}}`
- Ссылка должна быть абсолютной: `https://app.example.com/invite/{{token}}`
- Указать срок действия и предупреждение: «Если вы не ожидали это приглашение, проигнорируйте письмо»

### 4.6. Безопасность email

- Не хранить содержимое писем в логах (особенно токены)
- Использовать HTTPS для ссылок
- Токен — криптографически случайный (например, 32 байта, base64url), не поддающийся подбору

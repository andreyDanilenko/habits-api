# Задача: идеальная авторизация — безопасность, защита от DDoS и взлома

Цель: довести авторизацию до уровня «идеальной» с точки зрения безопасности, устойчивости к DDoS и типовым атакам (брутфорс, перебор, утечка данных, сессионные атаки).

---

## 1. Аутентификация и токены

| Мера | Описание | Статус |
|------|----------|--------|
| Access token в HttpOnly cookie | Уже есть | ✅ |
| Короткий срок жизни access token | Вынести в конфиг (например 15–60 мин) | 📋 |
| Refresh token | Отдельный долгоживущий токен в HttpOnly cookie, ротация при использовании | 📋 |
| Refresh endpoint | POST /auth/refresh по refresh cookie, возвращает новую пару токенов | 📋 |
| Blacklist/revocation | При logout инвалидировать refresh token (таблица или Redis) | 📋 |
| Один активный refresh на пользователя или семейство устройств | Опционально: при выдаче нового — инвалидировать старый | 📋 |

---

## 2. Защита от брутфорса и перебора

| Мера | Описание | Статус |
|------|----------|--------|
| Rate limit по IP | Уже есть (10/мин на auth) | ✅ |
| Rate limit в конфиге | `AUTH_RATE_LIMIT_N`, `AUTH_RATE_LIMIT_WINDOW` | 📋 |
| Redis для rate limit | Общий счётчик при нескольких инстансах API | 📋 |
| Account lockout | После N неудачных попыток (5–10) блокировка аккаунта на M минут | 📋 |
| Таблица login_attempts | `user_id` / `email`, `ip`, `success`, `created_at`; или кеш по email+IP | 📋 |
| Задержка при неудачном логине | Constant-time ответ, например минимум 200–500 ms перед ответом | 📋 |
| Нет user enumeration | Одинаковое сообщение и время при неверном email/пароле | ✅ |
| Dummy hash при отсутствии user | Constant-time сравнение с заглушкой | ✅ |

---

## 3. Защита от DDoS и злоупотреблений

| Мера | Описание | Статус |
|------|----------|--------|
| Rate limit на auth | Уже есть по IP | ✅ |
| Глобальный rate limit на API | Ограничение запросов с IP на все эндпоинты (например 100–200/мин) | 📋 |
| Rate limit на регистрацию | Отдельный лимит на POST /register с IP (например 3–5/час) | 📋 |
| Таймауты и лимиты размера тела | Ограничение размера request body, таймауты на чтение/запись | 📋 |
| Зарезервированные/заблокированные email | Список доменов или паттернов, запрещённых для регистрации | 📋 |

---

## 4. Защита от взлома и утечек

| Мера | Описание | Статус |
|------|----------|--------|
| Пароли — bcrypt | Уже есть | ✅ |
| Сложность пароля | Минимум длина (8), опционально: верхний/нижний регистр, цифры, спецсимволы | ✅/📋 |
| Нет пароля в логах и ответах | Проверить, что пароль нигде не логируется и не возвращается в JSON | 📋 |
| SQL-инъекции | Параметризованные запросы, whitelist для динамических частей | ✅ |
| Заголовки безопасности | X-Content-Type-Options, X-Frame-Options, CSP (где применимо) | 📋 |
| HTTPS в production | Cookie Secure=true, редирект HTTP→HTTPS | ✅ (по конфигу) |
| CSRF | SameSite cookie, при необходимости — проверка X-CSRF-Token для state-changing запросов | 📋 |

|------|----------|--------|

|------|----------|--------|

## 7. Аудит и мониторинг

| Мера | Описание | Статус |
|------|----------|--------|
| Логирование неудачных попыток входа | IP, email (или хеш), время — без паролей | 📋 |
| Алерты при аномалиях | Много неудачных попыток с одного IP или по одному аккаунту | 📋 |
| Метрики rate limit | Счётчики срабатываний лимитеров для дашборда | 📋 |

---

## Приоритеты внедрения

1. **Высокий:** Refresh token, account lockout, конфиг rate limit, Redis rate limit (при нескольких инстансах).
2. **Средний:** Глобальный rate limit, задержка при неудачном логине, заголовки безопасности, отзыв сессий при logout.
3. **Низкий:** CAPTCHA, подтверждение email, список активных сессий, расширенная политика паролей.

После выполнения пунктов из `BACKLOG/auth.md` и высокоприоритетных пунктов выше авторизация будет считаться «идеальной» по безопасности и защите от DDoS/взлома в рамках типовых требований.

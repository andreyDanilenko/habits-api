# Чек-лист приемки: Роли и права (Override semantics, кастомные роли)

## Методология проверки
- **Уровень тестирования**: Системное/интеграционное тестирование
- **Фокус**: Ролевая модель, override semantics, кастомные роли как основная роль участника
- **Тип проверок**: Функциональные + права доступа

---

## Блок 1: Системные роли (базовое поведение)

### 1.1 Список участников и отображение ролей
- [ ] OWNER видит всех участников workspace
- [ ] ADMIN видит всех участников workspace
- [ ] В списке участников отображается системная роль (OWNER, ADMIN, MEMBER, GUEST)
- [ ] Владелец workspace всегда имеет роль OWNER
- [ ] При создании workspace владелец автоматически получает роль OWNER

### 1.2 Смена системной роли
- [ ] OWNER может менять роль участника на ADMIN, MEMBER, GUEST
- [ ] ADMIN может менять роль участника на MEMBER, GUEST (не на OWNER)
- [ ] MEMBER не может менять роли других участников
- [ ] GUEST не может менять роли других участников
- [ ] Нельзя сменить свою собственную роль
- [ ] Нельзя сменить роль единственного OWNER (должен остаться хотя бы один)
- [ ] После смены роли участник получает соответствующий набор прав (GUEST — только чтение)

### 1.3 Права по системным ролям
- [ ] GUEST видит модули: Привычки, Дневник, CRM, Заметки (только просмотр)
- [ ] GUEST не видит настройки workspace, участников, модули
- [ ] MEMBER может создавать/редактировать в модулях (habits, crm, notes, journal)
- [ ] ADMIN может управлять участниками, модулями, ролями
- [ ] OWNER имеет полный доступ ко всем функциям workspace

---

## Блок 2: Кастомные роли

### 2.1 Создание кастомных ролей
- [ ] OWNER/ADMIN может создать кастомную роль на странице «Роли»
- [ ] При создании роли можно выбрать произвольный набор прав из каталога
- [ ] Можно создать роль «Только привычки» (habits:habit:read, habits:journal:read, workspace:module:read)
- [ ] Можно создать роль «Только CRM» (crm:deal:*, crm:contact:*, crm:company:*, workspace:module:read)
- [ ] Можно создать роль «Seller» с правами только на CRM
- [ ] Системные роли (OWNER, ADMIN, MEMBER, GUEST) нельзя редактировать или удалять

### 2.2 Назначение кастомной роли как основной
- [ ] В списке участников в выпадающем списке «Роль» отображаются кастомные роли (отдельная группа)
- [ ] OWNER/ADMIN может назначить участнику кастомную роль вместо системной
- [ ] При выборе кастомной роли участник получает ТОЛЬКО права этой роли (override semantics)
- [ ] Участник с кастомной ролью «Только привычки» видит только модуль Привычки
- [ ] Участник с кастомной ролью «Только CRM» видит только модуль CRM
- [ ] Можно вернуть участнику системную роль (OWNER/ADMIN/MEMBER/GUEST) из выпадающего списка

### 2.3 Override semantics (кастомная роль заменяет системную)
- [ ] Если у пользователя есть кастомная роль — используются ТОЛЬКО права кастомной роли
- [ ] Системные роли при наличии кастомной роли игнорируются
- [ ] Участник с ролью GUEST + кастомная «HabitsOnly» → видит только привычки (не всё как GUEST)
- [ ] API `/me/permissions` возвращает только права кастомной роли при override

## Блок 3: Скрытие модулей по ролям

### 3.1 Ограничение доступа к модулям
- [ ] Участник с ролью «Только привычки» не видит в меню: CRM, Заметки, Проекты
- [ ] Участник с ролью «Только CRM» не видит в меню: Привычки, Заметки, Проекты
- [ ] При прямом переходе по URL на недоступный модуль — редирект на доступный (например, /habits/dashboard)
- [ ] Список модулей в сайдбаре фильтруется по правам пользователя

### 3.2 API и бэкенд
- [ ] PermissionMiddleware (Casbin) корректно проверяет права для кастомных ролей
- [ ] Запросы к API без прав возвращают 403 Forbidden
- [ ] GetEffectivePermissions возвращает объединение прав при только системных ролях
- [ ] GetEffectivePermissions возвращает только права кастомных ролей при override

## Блок 4: UI и UX

### 4.1 Страница участников
- [ ] Выпадающий список ролей содержит: Системные (OWNER, ADMIN, MEMBER, GUEST) и Кастомные
- [ ] Текущая роль участника отображается корректно (в т.ч. кастомная по имени)
- [ ] Смена роли на кастомную сохраняется и отображается без перезагрузки
- [ ] Ошибка при смене роли отображается пользователю, список перезагружается

### 4.2 Страница ролей
- [ ] Список ролей содержит системные и кастомные
- [ ] Кастомные роли можно создавать, редактировать, удалять (если нет назначений)
- [ ] При редактировании роли можно изменить набор прав
- [ ] Роль с назначенными пользователями нельзя удалить

### 4.3 Навигация и доступ
- [ ] Пользователь с кастомной ролью видит только разрешённые пункты меню
- [ ] Роутер не допускает переход на страницы без прав (requirePermission)
- [ ] При смене workspace права пересчитываются

## Блок 5: Граничные случаи и безопасность

### 5.1 Владелец и единственный OWNER
- [ ] Нельзя понизить роль единственного OWNER
- [ ] Владелец workspace (workspaces.owner_id) всегда должен иметь доступ
- [ ] При удалении участника с ролью OWNER (если их несколько) — остальные OWNER сохраняются

### 5.2 Валидация
- [ ] API не принимает roleId системной роли для UpdateMemberRole (только role)
- [ ] API требует role или roleId при PATCH /workspaces/:id/members/:userId
- [ ] Невалидный roleId возвращает 404 или 400

### 5.3 Синхронизация
- [ ] user_workspaces.role и user_role_assignments синхронизированы
- [ ] При назначении кастомной роли в user_workspaces записывается имя роли
- [ ] Casbin политики обновляются при смене роли

### 5.4 Удаление кастомной роли
- [ ] При удалении кастомной роли пользователи с этой ролью автоматически переключаются на GUEST
- [ ] user_workspaces.role обновляется на GUEST
- [ ] user_role_assignments: старая роль удаляется, добавляется GUEST
- [ ] Casbin: группировки обновляются (user → role:GUEST)
- [ ] Удаление роли с назначенными пользователями не блокируется (раньше возвращалась ошибка)

---

## Блок 6: Роли под должности (будущее расширение)

### 6.1 Подготовка к ролям Seller, HR
- [ ] Можно создать роль «Seller» с правами только CRM
- [ ] Можно создать роль «HR» (когда модуль HR будет добавлен) с правами только HR
- [ ] Кастомная роль может иметь любой набор прав из permission_catalog
- [ ] permission_catalog содержит все необходимые права для модулей

## Критерии приёмки (итог)

| Критерий | Статус |
|----------|--------|
| GUEST можно ограничить до одного модуля (например, только привычки) | |
| Кастомная роль заменяет системную (override), а не расширяет | |
| В UI участников можно назначить кастомную роль как основную | |
| Участник с кастомной ролью видит только разрешённые модули | |
| API и бэкенд корректно проверяют права для кастомных ролей | |
| Роли под должности (Seller, HR) можно создавать через кастомные роли | |

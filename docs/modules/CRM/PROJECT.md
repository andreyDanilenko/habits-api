Масштабируемость в таких системах (SaaS) строится не на жестких внешних ключах (FOREIGN KEY) между модулями, а на архитектурных паттернах. Если вы свяжете tasks и crm_deals через классический REFERENCES, вы никогда не сможете разнести их по разным базам данных или микросервисам.
Чтобы система была масштабируемой и модульной, используйте следующие принципы:
1. Изоляция на уровне данных: Row Level Security (RLS)
Чтобы не забыть добавить WHERE workspace_id = ... в каждом запросе и исключить утечку данных между клиентами, используйте возможности PostgreSQL:
Вы включаете RLS для всех таблиц.
При каждом запросе устанавливаете переменную сессии SET app.current_workspace_id = '...'.
PostgreSQL автоматически фильтрует данные. Это база безопасности для масштабируемого SaaS.
2. Связность модулей: "Soft Links" (Мягкие связи)
Для масштабирования откажитесь от прямых FOREIGN KEY между таблицами разных модулей. Например, модуль Tasks не должен иметь констрейнт на таблицу CRM.
Как это сделать:
Используйте концепцию Global ID или Composite Link:
sql
CREATE TABLE task_links (
    task_id UUID NOT NULL,
    target_module VARCHAR(20) NOT NULL, -- 'crm', 'inventory', 'hr'
    target_entity_type VARCHAR(50) NOT NULL, -- 'deal', 'stock_item'
    target_id UUID NOT NULL, -- ID объекта в другом модуле
    PRIMARY KEY (task_id, target_id)
);
Используйте код с осторожностью.

Почему это масштабируемо:
Независимость: Модуль задач может работать и без CRM.
Шардирование: Если база вырастет, вы сможете вынести CRM на отдельный сервер. Foreign Key бы вам этого не позволил, а target_id — позволит.
3. Сквозные сущности (Shared Kernels)
Определите "Core" (ядро) системы, которое неизменно.
Workspaces — всегда в ядре.
Users — всегда в ядре.
Projects — сделайте частью ядра или "базовым модулем".
Все остальные модули (CRM, Tasks, Billing) «смотрят» на ядро, но не друг на друга. Если CRM нужно знать что-то о задаче, она спрашивает это через API или через таблицу связей.
4. Событийная модель (Event Driven) — пик масштабируемости
Когда вы захотите пойти дальше, модули будут общаться через события.
Действие: В CRM закрыта сделка.
Событие: CRM_DEAL_CLOSED.
Реакция: Модуль Tasks ловит это событие и автоматически создает задачу «Выставить счет».
Плюс: Модуль CRM ничего не знает о коде модуля Tasks.
Как быть с «Проектами»?
Чтобы иметь изолированные задачи для проектов, используйте Hierarchy Key (Иерархический ключ):
Project-based: Каждая запись имеет project_id. Если project_id пуст — это личная задача воркспейса.
Виртуальные проекты: Если модуля projects нет, вы просто скрываете поле в UI. В базе структура остается единой.
Практический совет по структуре таблиц для масштабирования:
Вместо одной огромной таблицы связей, используйте интерфейсные таблицы в каждом модуле:
Модуль	Ответственность
Core	workspaces, users, modules_registry
Projects	projects (id, workspace_id)
Tasks	tasks (id, workspace_id, parent_id, project_id)
CRM	deals (id, workspace_id, project_id)
Как они связываются?
Через project_id. Это общая «точка сборки». Если вы находитесь в проекте "Постройка дома", вы просто делаете:
SELECT * FROM tasks WHERE project_id = 'X' AND workspace_id = 'Y'
SELECT * FROM deals WHERE project_id = 'X' AND workspace_id = 'Y'
И на фронтенде агрегируете эти данные.

# Messaging и Realtime: почему не RabbitMQ и порядок внедрения

## 1. Почему не RabbitMQ (для чатов и уведомлений)

### Контекст

Для **realtime чатов и уведомлений** нужны:
- **Низкая задержка** (< 100 ms)
- **Push-модель** — сервер сразу шлёт клиенту
- **Presence** — кто онлайн
- **Сохранение истории** (опционально)

### Сравнение

| Критерий | RabbitMQ | Redis Pub/Sub | NATS | Kafka |
|----------|----------|---------------|------|-------|
| **Латентность** | 1–5 ms | < 1 ms | < 1 ms | 5–50 ms |
| **Паттерн** | Queue (pull) | Pub/Sub (push) | Pub/Sub | Log (pull) |
| **Realtime** | Нет, нужен polling | Да | Да | Нет |
| **История** | Есть (persistent) | Нет | Нет | Есть (replay) |
| **Сложность** | Средняя | Низкая | Низкая | Высокая |

### Почему RabbitMQ не подходит для realtime

1. **RabbitMQ = очередь задач**  
   Сообщения забирает consumer (pull). Для realtime нужен push: сервер сам шлёт клиенту по WebSocket.

2. **Нет нативной связи с WebSocket**  
   Придётся делать bridge: RabbitMQ → worker → WebSocket. Лишний hop и задержка.

3. **Оверхед для realtime**  
   AMQP, ACK, подтверждения — для «сейчас отправил, сейчас получил» это избыточно.

### Что лучше для чатов и уведомлений

| Сценарий | Рекомендация |
|----------|--------------|
| **Realtime push (чаты, уведомления)** | **Socket.io + Redis** (или NestJS Gateway + Redis adapter) |
| **Фоновые задачи (email, отчёты)** | RabbitMQ или Bull (Redis) |
| **Event sourcing, replay** | Kafka |
| **Простой pub/sub между сервисами** | NATS или Redis |

### Архитектура realtime (без RabbitMQ)

```
┌─────────────┐     WebSocket      ┌─────────────────┐     Redis Pub/Sub
│   Client    │ ◄─────────────────► │ Realtime Service │ ◄─────────────────►
│  (Browser)  │                     │     (NestJS)     │     │ Go API (монолит) │
└─────────────┘                     └─────────────────┘     └─────────────────┘
                                            │
                                            │ при событии (сделка создана,
                                            │ привычка выполнена) — publish
                                            │ в Redis channel
                                            ▼
                                   ┌─────────────────┐
                                   │  Redis          │
                                   │  channel: ws/   │
                                   │  workspace:{id} │
                                   └─────────────────┘
```

**Go API** после создания сделки/привычки делает `PUBLISH ws:workspace:{id} {event}`.  
**Realtime Service** подписан на Redis и рассылает по WebSocket всем подключённым клиентам workspace.

## 2. Когда RabbitMQ всё же нужен

| Сценарий | RabbitMQ |
|----------|----------|
| Очередь задач (отправка email, генерация отчётов) | ✅ |
| Гарантированная доставка | ✅ |
| Retry, dead letter | ✅ |
| Разделение нагрузки между воркерами | ✅ |

То есть RabbitMQ — для **асинхронных фоновых задач**, а не для realtime.

## 3. Realtime сначала, потом дележка

### Рекомендация: **сначала realtime, потом микросервисы**

```
Этап 1: Realtime Service (чаты, уведомления)
    │
    │  Монолит Go API остаётся как есть
    │  Монолит публикует события в Redis
    │  NestJS Realtime подписан на Redis
    │
    ▼
Этап 2: Декомпозиция (микросервисы)
    │
    │  Монолит разбивается на сервисы
    │  Realtime Service уже есть и работает
    │  Каждый новый сервис тоже публикует в Redis
    │
    ▼
Этап 3: Готово
```

### Почему так

1. **Realtime — отдельный сервис с самого начала**  
   NestJS + Socket.io уже в проекте. Его можно сразу вынести в отдельный процесс и не трогать при дальнейшей декомпозиции.

2. **Проще отладить на монолите**  
   Один источник событий (Go API). Понятно, откуда идут события.  
   При разбиении на микросервисы источников много — сложнее отлаживать.

3. **Единая модель событий**  
   Сначала определится формат: `{ type, workspace_id, entity_type, entity_id, payload }`.  
   Потом этот же формат используют все новые сервисы.

4. **Пользовательская ценность быстрее**  
   Чаты и уведомления дают сразу заметный эффект. Декомпозиция — внутренняя оптимизация.

5. **Realtime не зависит от декомпозиции**  
   Realtime Service получает события из Redis.  
   Не важно, кто публикует: монолит или отдельный CRM/Habits сервис.

### План внедрения

| Шаг | Действие |
|-----|----------|
| 1 | Создать Realtime Service (NestJS + Socket.io + Redis adapter) |
| 2 | В Go API: после важных действий (сделка, привычка, приглашение) — `PUBLISH` в Redis |
| 3 | Realtime подписывается на `ws:workspace:{id}`, шлёт клиентам по WebSocket |
| 4 | Добавить чаты (таблицы `chats`, `messages`) и уведомления |
| 5 | После стабилизации — начинать декомпозицию монолита |

### Итог

- **RabbitMQ** — для очередей задач (email, отчёты), не для realtime.
- **Redis Pub/Sub** — для realtime (чаты, уведомления) вместе с Socket.io.
- **Realtime сначала** — проще, быстрее ценность, единая модель событий.
- **Декомпозиция потом** — Realtime Service уже готов и не меняется при разбиении.

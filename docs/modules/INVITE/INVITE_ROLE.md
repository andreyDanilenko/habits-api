## 2. Приглашения пользователей в workspace

### 2.1. Что нужно реализовать

**Цель:** ADMIN и OWNER должны иметь возможность приглашать новых участников в workspace.

**Типовой процесс приглашения** :

```
[ADMIN] → [Заполняет email и роль] → [Система отправляет email] → [Пользователь переходит по ссылке] → [Пользователь становится участником]
```

### 2.2. Варианты приглашений

#### Вариант A: Приглашение по email (рекомендуется)
- ADMIN вводит email нового участника
- Выбирает системную роль (MEMBER/GUEST) и кастомные роли
- Система отправляет email со ссылкой-приглашением
- При переходе по ссылке пользователь либо регистрируется, либо входит в систему
- После входа автоматически добавляется в workspace с указанными ролями 

#### Вариант B: Приглашение по ссылке
- ADMIN генерирует ссылку-приглашение
- Может установить срок действия ссылки
- Может настроить, какие роли получит новый пользователь
- Ссылку можно отправить любым способом (email, мессенджер) 

#### Вариант C: Массовое приглашение
- Возможность пригласить несколько пользователей одновременно (до 5 за раз) 
- У всех приглашённых одинаковые роли

### 2.3. Временный доступ (гостевые пользователи)

Важно поддерживать сценарий временного доступа :

- При приглашении можно выбрать тип доступа: **постоянный** или **временный**
- Для временного доступа указать срок (например, 30 дней)
- По истечении срока доступ автоматически блокируется
- В интерфейсе видно, когда истекает доступ у гостя

### 2.4. Интеграция с системой прав

При приглашении нужно назначать:

| Тип роли | Как задаётся |
|----------|--------------|
| **Системная роль** | MEMBER или GUEST (выбирается в форме) |
| **Кастомные роли** | Можно выбрать одну или несколько |
| **Индивидуальные права** | Можно добавить временные права |

### 2.5. API для приглашений

```http
POST /api/v1/workspaces/{workspaceId}/invitations
{
  "email": "user@example.com",
  "systemRole": "MEMBER",  // или "GUEST"
  "roleIds": ["uuid1", "uuid2"],  // кастомные роли
  "permissions": [  // индивидуальные права
    {"permissionId": "uuid3", "expiresAt": "2026-04-01T00:00:00Z"}
  ],
  "expiresIn": 2592000  // срок действия ссылки в секундах (опционально)
}
```

```http
POST /api/v1/workspaces/{workspaceId}/invitations/bulk
{
  "emails": ["user1@example.com", "user2@example.com"],
  "systemRole": "MEMBER",
  "roleIds": ["uuid1", "uuid2"]
}
```

```http
GET /api/v1/workspaces/{workspaceId}/invitations  // список активных приглашений
DELETE /api/v1/workspaces/{workspaceId}/invitations/{invitationId}  // отозвать приглашение
```

## 3. Видимость на уровне модулей

### 3.1. Как это работает сейчас

У нас есть система модулей (`modules`, `workspace_modules`), которая определяет, какие модули **вообще включены** в workspace.

```sql
-- Какие модули активны в workspace
workspace_modules (
    workspace_id,
    module_id,
    status  -- 'active', 'trial', 'disabled'
)
```

**Текущая логика:**
- Если модуль отключён в workspace, никто его не видит
- Если модуль включён, то доступ к нему регулируется правами

### 3.2. Видимость модулей для конкретного пользователя

У нас уже есть механизм для этого:

1. **Проверка через ModuleMiddleware** — определяет, к какому модулю относится запрос
2. **Проверка через PermissionMiddleware** — проверяет конкретные права

**Как это работает:**
- Если у пользователя нет **ни одного права** на модуль, он не увидит этот модуль в меню
- Если есть хотя бы одно право (например, `crm:deal:read`), модуль показывается

### 3.3. Пример

```typescript
// Навигационное меню строится динамически
const menuItems = [
  {
    name: 'CRM',
    path: '/crm',
    visible: canAny([
      Perm.crm.deal.read,
      Perm.crm.contact.read,
      Perm.crm.company.read
    ])
  },
  {
    name: 'Привычки',
    path: '/habits',
    visible: canAny([
      Perm.habits.habit.read,
      Perm.habits.journal.read
    ])
  }
];
```

### 3.4. Вывод по модулям

✅ **Уже работает:** Видимость модулей автоматически настраивается через права. Если у пользователя нет прав на чтение ни одной сущности модуля, модуль скрывается.

❌ **Чего нет:** Возможности принудительно скрыть модуль даже при наличии прав (но это редко нужно).

## 4. Видимость на уровне проектов

### 4.1. Текущая ситуация с проектами

У нас есть модуль `Projects`, который позволяет группировать сущности:

```sql
projects (
    id,
    workspace_id,
    name,
    description
)

project_entities (
    project_id,
    entity_type,  -- 'crm_contact', 'crm_deal', 'habit'
    entity_id
)
```

**Сейчас:** Если пользователь имеет доступ к сущности (например, к сделке), он видит её во всех проектах, куда она добавлена.

### 4.2. Нужна ли приватность проектов?

**Сценарии:**

1. **Публичный проект** — все участники workspace видят проект и его сущности (если имеют доступ к сущностям)
2. **Приватный проект** — проект виден только определённым пользователям/ролям

### 4.3. Как это можно реализовать

#### Вариант A: Роли на уровне проектов

Добавить таблицу `project_roles` :

```sql
CREATE TABLE project_roles (
    id UUID PRIMARY KEY,
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    name VARCHAR(100) NOT NULL,  -- 'Project Manager', 'Project Viewer'
    permissions JSONB,  -- специфичные для проекта права
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE TABLE project_role_assignments (
    id UUID PRIMARY KEY,
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role_id UUID NOT NULL REFERENCES project_roles(id) ON DELETE CASCADE,
    assigned_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

**Плюсы:** Гибкость, можно настроить разные уровни доступа внутри проекта
**Минусы:** Усложнение модели, нужно добавлять проверки везде

#### Вариант B: Приватные проекты через visibility flag

```sql
ALTER TABLE projects ADD COLUMN visibility VARCHAR(20) DEFAULT 'public';
ALTER TABLE projects ADD COLUMN visible_to JSONB;  -- массив ID пользователей/ролей
```

**Плюсы:** Проще реализовать
**Минусы:** Меньше гибкости, нет гранулярных прав внутри проекта

#### Вариант C: Использовать существующую систему прав

Можно добавить права вида `project:project:view`, `project:project:manage` и назначать их как индивидуальные права или через роли.

**Плюсы:** Использует уже существующую инфраструктуру
**Минусы:** Нужно будет для каждого проекта создавать отдельные права (динамические)

### 4.4. Рекомендация

Начать с **Варианта C**, так как он использует уже существующую систему прав и не требует новых таблиц:

1. Добавить в `permission_catalog` новые права:
   - `project:project:view` — просмотр проекта
   - `project:project:manage` — управление проектом

2. Для каждого конкретного проекта создавать "экземплярные" права? Это сложно, так как права в каталоге статичны.

Более правильное решение — **Вариант A** с отдельными ролями для проектов, но это отдельная большая задача.

## 5. Выборочное скрытие данных

### 5.1. Три уровня контроля доступа 

| Уровень | Что контролирует | Пример |
|---------|------------------|--------|
| **Permissions (права)** | Доступ к сущностям на уровне БД | Может ли пользователь видеть сделки вообще |
| **Visibility (видимость)** | Какие UI элементы показывать | Видит ли кнопку "Создать" |
| **Filters (фильтры)** | Какие записи показывать в списке | Видит только свои сделки |

### 5.2. Что у нас уже есть

✅ **Permissions** — полностью работают (через Casbin)
✅ **Visibility** — работает через `PermissionGuard`
❌ **Filters** — пока нет механизма ограничения видимости записей

### 5.3. Нужно ли фильтровать данные?

**Сценарии:**

1. **Менеджер видит только свои сделки**
2. **Руководитель видит сделки своего отдела**
3. **Региональный менеджер видит сделки только своего региона**

### 5.4. Как это можно реализовать

#### Вариант A: Data Scope 

Добавить понятие "область данных" (data scope) для ролей:

```typescript
enum DataScope {
  SELF = 'self',           // только свои записи
  TEAM = 'team',           // записи своей команды
  DEPARTMENT = 'department', // записи своего отдела
  COMPANY = 'company'      // все записи
}
```

**Как это работает:**
- При назначении роли указывается data scope
- При запросе списка сущностей автоматически добавляется фильтр по `owner_id` или другому полю

#### Вариант B: Политики Casbin для фильтрации

Casbin может не только проверять права, но и возвращать условия для фильтрации :

```go
// Casbin может вернуть что-то вроде:
filter = "owner_id = 'user123' OR team_id IN ('team1', 'team2')"
```

#### Вариант C: Row Level Security в PostgreSQL

Использовать встроенные возможности PostgreSQL для ограничения доступа на уровне строк:

```sql
CREATE POLICY deal_policy ON crm_deals
    USING (owner_id = current_user_id() OR team_id IN (user_teams()));
```

### 5.5. Рекомендация

Пока **не реализовывать** полноценную систему фильтрации данных. Это отдельная большая задача, которая требует:

- Анализа всех запросов к БД
- Добавления полей `owner_id`, `team_id` во все таблицы
- Решения о том, как определять "команды" и "отделы"
- Проработки производительности

### 6.2. API спецификация для приглашений

```typescript
// POST /api/v1/workspaces/{workspaceId}/invitations
interface CreateInvitationRequest {
  email: string;
  systemRole: 'MEMBER' | 'GUEST';
  roleIds?: string[];
  permissions?: {
    permissionId: string;
    expiresAt?: string;
  }[];
  expiresIn?: number; // срок действия ссылки в секундах (по умолчанию 7 дней)
}

// Ответ
interface InvitationResponse {
  id: string;
  email: string;
  workspaceId: string;
  invitedBy: {
    id: string;
    name: string;
    email: string;
  };
  systemRole: 'MEMBER' | 'GUEST';
  roleIds: string[];
  permissions: {
    permissionId: string;
    expiresAt?: string;
  }[];
  status: 'PENDING' | 'ACCEPTED' | 'EXPIRED' | 'CANCELLED';
  inviteLink: string; // ссылка, которую можно скопировать
  expiresAt: string;
  createdAt: string;
}

// GET /api/v1/workspaces/{workspaceId}/invitations
interface ListInvitationsResponse {
  invitations: InvitationResponse[];
}

// DELETE /api/v1/workspaces/{workspaceId}/invitations/{invitationId}
// 200 OK

// POST /api/v1/invitations/{invitationId}/accept
// Принимается без тела, просто переход по ссылке
```

### 6.3. Таблица invitations

```sql
CREATE TABLE invitations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    email VARCHAR(255) NOT NULL,
    invited_by UUID NOT NULL REFERENCES users(id),
    system_role VARCHAR(20) NOT NULL CHECK (system_role IN ('MEMBER', 'GUEST')),
    role_ids UUID[],  -- массив ID кастомных ролей
    permissions JSONB,  -- массив { permissionId, expiresAt }
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'ACCEPTED', 'EXPIRED', 'CANCELLED')),
    token VARCHAR(255) UNIQUE NOT NULL,  -- уникальный токен для ссылки
    expires_at TIMESTAMP NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    accepted_at TIMESTAMP
);

CREATE INDEX idx_invitations_token ON invitations(token);
CREATE INDEX idx_invitations_email ON invitations(email);
CREATE INDEX idx_invitations_status ON invitations(status);
CREATE INDEX idx_invitations_expires ON invitations(expires_at) WHERE status = 'PENDING';
```

## 8. Рекомендации

### 8.1. Что сделать сейчас

1. **Реализовать приглашения пользователей** — это базовый функционал, без которого workspace не может расти
2. **Убедиться, что динамическое меню работает** — модули должны скрываться при отсутствии прав

### 8.2. Что отложить

1. **Приватные проекты** — требует отдельного анализа, не критично для MVP
2. **Фильтрация данных (data scope)** — сложная задача, нужна только в больших организациях

### 8.3. Интеграция с существующей системой

✅ **Всё, что мы делаем, опирается на существующую систему прав:**
- Приглашения используют те же роли и права
- Видимость модулей уже работает через права
- Проекты могут использовать ту же модель

### 8.4. Ответы на вопросы

> "Нужно ли нам приглашение пользователей организовать?"

**Да, это следующий логический шаг.** У нас есть система ролей, но нет способа добавлять новых участников.

> "Можем ли мы настраивать видимость на уровне проектов?"

**Пока нет, но можно добавить.** Это отдельная задача, которую стоит проработать после приглашений.

> "Можно ли выборочно скрывать данные для пользователя?"

**На уровне сущностей — да (через права). На уровне отдельных записей — пока нет.** Фильтрация записей (row-level security) требует отдельной реализации.

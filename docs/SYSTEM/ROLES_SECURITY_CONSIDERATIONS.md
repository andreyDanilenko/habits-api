# Безопасность гибкой системы ролей

## Потенциальные проблемы и решения

---

## 1. Коллизия имён ролей (критично)

### Проблема
В Casbin субъект роли задаётся как `role:<name>`. Системные роли (OWNER, ADMIN, MEMBER, GUEST) и кастомные роли используют одно пространство имён. Если создать кастомную роль с именем `OWNER`, она будет иметь тот же Casbin-субъект `role:OWNER`, что и системная роль — **конфликт и потенциальная эскалация привилегий**.

### Решение
- **Запретить** создание и переименование кастомных ролей в имена системных: `OWNER`, `ADMIN`, `MEMBER`, `GUEST`.
- В `CreateRole` и `UpdateRole` добавить проверку: `if strings.ToUpper(name) in ["OWNER","ADMIN","MEMBER","GUEST"] → error`.

---

## 2. Индивидуальные права (user_permissions)

### Проблема
`user_permissions` добавляются к правам ролей (union). Пользователь с ролью GUEST может получить индивидуальный грант `crm:deal:delete` и обойти ограничения роли.

### Решение
- Ограничить выдачу индивидуальных прав только OWNER/ADMIN workspace.
- Проверять в API `GrantPermission`: вызывающий должен иметь `workspace:role:manage` или быть OWNER/ADMIN.
- Рассмотреть политику: при override (кастомная роль) индивидуальные права либо игнорируются, либо требуют явного флага `allow_individual_override`.

---

## 3. Наследование ролей (role_inheritance)

### Проблема
Кастомная роль может наследовать от системной (например, `Seller` ← `GUEST`). Если разрешить наследование от OWNER/ADMIN, пользователь получит полные права через кастомную роль.

### Решение
- Запретить наследование кастомной роли от OWNER или ADMIN.
- При `AddRoleInheritance`: если `parent` — системная роль OWNER/ADMIN → error.
- Документировать: наследование только для расширения прав внутри «безопасных» ролей.

---

## 4. Удаление роли и fallback на GUEST

### Проблема
При удалении кастомной роли пользователи переключаются на GUEST. GUEST имеет read на все модули. Если у пользователя была роль «Только привычки», после удаления роли он получит **больше** прав (доступ ко всем модулям).

### Решение
- **Текущее поведение** приемлемо как «безопасный по умолчанию» fallback (минимальная системная роль).
- **Альтернатива**: настраиваемый fallback на уровне workspace (например, `workspace.default_role_on_custom_deleted = GUEST | MEMBER`).
- Уведомлять админа при удалении роли с назначениями: «N пользователей переключены на GUEST».

---

## 5. Проверка прав на бэкенде

### Проблема
Фронтенд скрывает UI по правам, но API может вызываться напрямую. Без проверки Casbin на каждом эндпоинте — обход ограничений.

### Решение
- **PermissionMiddleware** должен проверять Casbin для всех защищённых маршрутов.
- Маппинг `(method, path) → (obj, act)` должен покрывать все эндпоинты модулей (CRM, habits, notes и т.д.).
- Режим «log-only» — только для отладки; в проде — блокировка 403 при отсутствии права.

---

## 6. Изоляция workspace

### Проблема
Роли привязаны к workspace. Ошибка в передаче `workspace_id` (домена в Casbin) может привести к проверке прав в неправильном workspace.

### Решение
- Всегда извлекать `workspace_id` из контекста/URL, не из тела запроса.
- В Casbin использовать домен: `Enforce("user:"+userID, workspaceID, obj, act)`.
- Проверять, что `role.WorkspaceID == workspaceID` при назначении роли.

---

## 7. Аудит и расследование

### Проблема
Без логов сложно выяснить, кто и когда изменил роли/права, что затрудняет расследование инцидентов.

### Решение
- Логировать: назначение/снятие ролей, выдачу/отзыв индивидуальных прав, создание/удаление/изменение кастомных ролей.
- Сохранять: `user_id`, `target_user_id`, `action`, `role_id`, `workspace_id`, `timestamp`.
- Рассмотреть таблицу `audit_log` для долгосрочного хранения.

---

## 8. Глобальный ADMIN

### Проблема
Пользователь с `users.role = ADMIN` обходит проверки workspace-ролей и получает полный доступ ко всем workspace.

### Решение
- Глобальный ADMIN — осознанное решение для суперадминов.
- Ограничить число таких пользователей, хранить их ID в конфиге/БД.
- Логировать все действия глобального ADMIN.

---

## 9. Race conditions при смене ролей

### Проблема
Параллельные запросы: смена роли и проверка прав могут выполняться в разном порядке, что даёт кратковременное несоответствие.

### Решение
- Casbin загружает политики из БД; после `SavePolicy` изменения видны.
- Использовать транзакции при обновлении `user_workspaces` + `user_role_assignments` + Casbin в одном flow.
- При высокой нагрузке — кэш Casbin с инвалидацией при изменении прав.

---

## 10. Валидация permission_catalog

### Проблема
При создании роли передаётся массив `permissions` (строки `module:entity:action`). Невалидные или несуществующие права могут игнорироваться или приводить к ошибкам.

### Решение
- В `CreateRole`/`UpdateRole`: проверять каждое право по `permission_catalog` (или белому списку).
- Отклонять права, которых нет в каталоге.
- Не добавлять в Casbin политики для неизвестных `(obj, act)`.

# План масштабных интеграций ERP ↔ n8n (чистая архитектура)

Документ опирается на идеи из `tasks_n8n.md` и на **уже существующие таблицы** схемы (см. `docs/schema/NEW_MIGRATE.sql` / миграции). Цель — выстроить предсказуемую «прошивку» без размазывания логики по Go, Nest и n8n.

---

## 1. Роли систем (кто за что отвечает)

| Слой | Сервис | Ответственность |
|------|--------|-----------------|
| **Домен и данные** | **Go (habits-api / ERP)** | CRUD, права, транзакции, инварианты бизнеса, запись в Postgres |
| **Интеграционный шлюз + realtime** | **Nest (nest-satellite)** | Приём событий от n8n, валидация ключа, вызов Go **только через HTTP API** (или публикация в Redis для внутренних подписчиков), WebSocket в браузер |
| **Оркестрация внешнего мира** | **n8n** | Расписания, внешние API (Telegram, GitHub, почта, ИИ), маршрутизация, ретраи, «склейка» нескольких провайдеров |

**Правило:** n8n **не** пишет напрямую в БД ERP. Любое изменение сущности — через публичный или internal HTTP API Go (или через явный сервисный контракт, который вы позже вынесете в отдельный BFF).

**Почему Nest, а не только Go:** уже есть WebSocket (`NotificationsGateway`), Redis pub/sub и паттерн internal endpoint. Nest удобен как **тонкий integration layer**: не дублировать всю бизнес-логику ERP, но централизовать «вход извне» и пуш в UI.

## 2. Опора на существующие таблицы

### Ядро мультиарендности и пользователей
- `users`, `workspaces`, `user_workspaces`, `user_preferences`
- `modules`, `workspace_modules`, `user_module_licenses` — включение модулей и лицензии

**Использование в интеграциях:** каждое событие и каждый вызов API должны нести `workspace_id` (и при необходимости `user_id`), чтобы не смешивать данные воркспейсов.

### CRM
- `crm_contacts`, `crm_companies`, `crm_deals`, `crm_pipelines`, `crm_stages`
- `crm_activities`, `crm_activity_files`, `crm_activity_reminders`

**Связь с идеями из `tasks_n8n.md`:** сделки, этапы, активности, напоминания — естественная точка для «истории переписки», NPS, реактивации лидов.

### Задачи
- `tasks`, `task_entity_links` (связь задачи с CRM и др.)
- `task_comments`, `task_task_links`, `task_attachments`, `task_time_entries`

**Связь:** «создать задачу из Telegram», «подзадачи при смене стадии», «тайм-трек из бота» — всё мапится на эти таблицы через Go API.

### Уведомления в продукте
- `notifications` — персистентная лента в приложении

**Связь:** n8n или Nest могут инициировать запись уведомления через существующий API уведомлений (как договоритесь в контракте).

### Универсальные интеграции (чистая база)
- `user_integrations` — `user_id`, `provider`, `external_id`, `settings` (JSONB)

**Назначение:** Telegram chat_id, GitHub installation id, токены ссылки на OAuth refresh (лучше хранить reference + шифрование, не сырой токен в открытом виде в JSONB без политики).

### Активность / аудит
- `activities` — лента «что произошло» в воркспейсе

**Связь:** важные автоматические действия из интеграций стоит отражать записью активности (через Go), чтобы в UI была прозрачность.

## 3. Контракт обмена (единая точка входа в n8n)

Уже заложено в `N8N_message.md` / `main-gateway`:

- **Вход:** `POST .../webhook/gateway/events`
- **Поля:** `secret`, `event_type`, `user_id`, `workspace_id` (рекомендуется добавить в payload стандарта), `payload`

**Правила:**
1. Список `event_type` — **версионируемый каталог** (документ или enum в коде).
2. Любое новое событие сначала описывается контрактом (JSON schema или таблица в docs), потом добавляется ветка в n8n.
3. Секреты только в env / secret store, не в workflow JSON.

---

## 4. Обратный поток: внешний мир → ERP

Примеры: Telegram, GitHub webhook, email.

**Цепочка:**

`Внешний сервис → n8n (webhook) → Nest (internal) → Go API → БД` — n8n **не** вызывает Go напрямую; пример: `POST /internal/integrations/telegram/confirm` в Nest проксируется в Go.

**Правила:**
1. **Идентификация пользователя:** после привязки Telegram хранить связь в `user_integrations` (`provider = 'telegram'`, `external_id` = chat_id или telegram user id — зафиксировать одно значение в контракте).
2. **Авторизация действия:** n8n передаёт в backend `user_id` + `workspace_id` только если они восстановлены из доверенного маппинга; иначе — отказ.
3. **Идемпотентность:** для webhook’ов от GitHub/Telegram использовать ключ идемпотентности (header/event id) и таблицу обработанных событий при росте нагрузки (отдельная миграция при необходимости).

## 5. Фазы внедрения (от MVP к масштабу из `tasks_n8n.md`)

### Фаза A — Фундамент (1–2 недели продуктово)
- Один активный workflow `Main Gateway` + контракт событий.
- Nest: единый internal приём + опционально прокси вызовов к Go.
- Go: минимальный набор **internal** или **service** endpoints: «создать задачу», «добавить CRM activity», «обновить стадию сделки» — строго с проверкой прав.
- Таблица `user_integrations` как единственный слой «пользователь ↔ внешний id» для новых фич.

**Идеи из `tasks_n8n.md`, которые попадают сюда без тяжёлых доработок схемы:**  
умные дедлайны (уведомление), отчёт за день (агрегация + сообщение), простая реактивация по таймеру (если есть поле `updated_at` у сделки — использовать запросом из n8n к API).

### Фаза B — CRM+ и задачи (2–4 недели)
- События из Go при смене стадии сделки → `event_type` → n8n → подзадачи, Telegram, календарь.
- Обратно: Telegram команда → n8n → Go «создать задачу» с `task_entity_links` на сделку.

**Таблицы:** `crm_deals`, `crm_stages`, `tasks`, `task_entity_links`, `activities`.

### Фаза C — Документы, финансы, маркетинг (по приоритету)
- Новые сущности или поля в CRM/Finance по мере необходимости; n8n не опережает схему БД.

### Фаза D — ИИ, скрапинг, LinkedIn (высокий риск ToS/GDPR)
- Выносить в отдельные политики и согласия; технически — отдельные workflow и ограничение rate limit.

## 6. Правила «чистой» интеграции (обязательные)

1. **Один вход событий из приложения в n8n** — через gateway webhook и каталог `event_type`.
2. **Один слой для realtime в браузер** — Nest WebSocket; n8n не подключается к сокетам клиента напрямую.
3. **Go остаётся источником истины** по данным; n8n — по внешним API и сценариям.
4. **Никаких секретов в экспортируемых JSON workflow** — только `$env` / credentials n8n.
5. **Prod vs test URL** — `webhook` только при `Active`; локально для Telegram — tunnel.
6. **Версионирование workflow** — git-хранение JSON в `deployment/n8n/workflows/` + ручной или CI импорт на сервер.
7. **Логи и отладка** — execution в n8n + structured logs в Go на internal endpoints.

---

## 7. Сценарий «свои интеграции» (для клиентов / воркспейсов)

Минимальная модель без перегруза схемы:

1. **Подключение провайдера** — строка в `user_integrations` или отдельная таблица `workspace_integrations` (если интеграция на уровне компании, а не пользователя) — при росте продукта.
2. **Шаблон workflow** — пользователь не редактирует JSON; вы даёте:
   - каталог готовых сценариев (как «пресеты»),
   - или UI «включить интеграцию X» с настройкой только разрешённых полей в `settings` JSONB.
3. **Изоляция:** webhook path или секрет на воркспейс (`settings` содержит `webhook_secret`, `workspace_id`).

Более зрелый вариант позже: таблица `integration_definitions` + `integration_bindings` — если понадобится marketplace интеграций.

## 8. Мощность n8n и польза для ERP (кратко)

- **Скорость изменений:** маркетинг и поддержка могут менять сценарии без релиза Go.
- **Надёжность доставки:** ретраи, ветвления, алерты при ошибке.
- **Склейка сервисов:** Telegram + почта + Google + GitHub в одном потоке.
- **Ограничение:** сложная бизнес-логика и права — только в Go; n8n не заменяет ERP.

## 9. Следующие артефакты (рекомендуемый backlog)

1. Документ **каталога `event_type`** с примером `payload` для каждого.
2. В Go: набор **internal** endpoints под n8n/Nest (создание задачи, движение сделки, запись activity).
3. В Nest: **единый** `POST /integrations/n8n/...` или расширение текущего паттерна с проксированием на Go.
4. Политика хранения секретов в `user_integrations.settings`.
5. Для GitHub: webhook в n8n → проверка подписи → вызов Go «привязать PR к задаче».

## 10. Связь с `tasks_n8n.md`

Файл `tasks_n8n.md` — **каталог идей**. Этот документ — **как встроить идеи в архитектуру**. При планировании спринта помечайте каждую идею тегами:

- **DB-ready** — хватает текущих таблиц  
- **API-gap** — нужен новый endpoint Go  
- **policy** — юридические/ToS риски (LinkedIn, массовая рассылка)  
- **n8n-only** — достаточно workflow без изменения схемы

Так вы не расползётесь по «интеграциям ради интеграций» и сохраните чистую линию между ERP, Nest и n8n.

## 11. Актуальный фокус: Telegram → GitHub → календарь

### 11.1 Уточнение по Telegram (что уже «мультиюзер», чего не хватает)

- **Один бот на всех** — нормально: у каждого пользователя свой личный чат с ботом и свой `chat_id`. Разделение — в БД (связь `user_id` ↔ `telegram_chat_id`), не в отдельных ботах.
- В репозитории уже есть цепочка **привязки**: UI → `POST .../integrations/telegram/link` → deep-link `t.me/bot?start=token` → n8n `telegram-connect` → `POST .../integrations/telegram/confirm` → таблица **`telegram_user_links`** (плюс одноразовые токены).
- Workflow **Main Gateway** шлёт в Telegram, если в теле запроса есть **`chat_id`**, иначе подставляется запасной **`TELEGRAM_USER_CHAT_ID`** из env (режим «один чат для тестов»).

**Пробел, который нужно закрыть для «каждый получает свои уведомления»:** при доменном событии (создана задача, назначен исполнитель, упоминание и т.д.) **бэкенд должен сам** (или через Nest):

1. По `user_id` получателя прочитать `telegram_chat_id` из `telegram_user_links` (и учесть `is_enabled`, если поле используется).
2. Если привязки нет — **не** звать Telegram (или только in-app уведомление).
3. Вызвать `POST .../webhook/gateway/events` с `secret`, `event_type`, `user_id`, **`chat_id`**, `payload` (как в `N8N_message.md`).

Сейчас в Go нет исходящих вызовов к n8n gateway — это следующий логичный шаг после стабильного `setWebhook` и активных workflow на проде/туннеле в dev.

**Целесообразный минимум по Telegram:** 1–2 типа событий (например `task.created` для исполнителя и `user.mention`) + единая маленькая функция «разрешить user_id → chat_id и дернуть gateway».

### 11.2 Порядок внедрения (рекомендация)

| Порядок | Направление | Почему так |
|---------|-------------|------------|
| **1** | **Telegram: привязка + доставка** | Уже есть БД и n8n; остаётся связать доменные события с gateway и `chat_id`. Без этого второй этап не даёт предсказуемого UX. |
| **2** | **GitHub ↔ задачи** | Нужны OAuth/GitHub App, хранение связи repo/issue ↔ `task_id` (через `task_entity_links` или отдельное поле), webhook с проверкой подписи, идемпотентность. Сложнее и шире поверхность безопасности. |
| **3** | **Сделки ↔ календарь** | OAuth Google/Microsoft, маппинг «сделка / дедлайн ↔ событие», политика синхронизации (одностороння vs двусторонняя). Удобно начинать с **одностороннего push** из ERP в календарь. |

### 11.3 GitHub и календарь — что заложить заранее (без полной реализации)

- Тот же принцип, что в §4: **внешний webhook → n8n → internal вызов Go**; мутации только через API.
- Связь сущностей: **`task_entity_links`** (или расширение) для привязки задачи к issue/PR; для сделок — либо поля в CRM, либо отдельная таблица «внешний календарь event id», когда появится реальная синхронизация.
- Универсальная модель **`user_integrations`** может со временем **дополнить** специализированные таблицы (OAuth refresh, installation id), не ломая текущие `telegram_user_links`.

# Часть 1. Фундамент: зачем система так устроена, мультитенантность и первые таблицы

**Связь с общим планом:** [plan.md](./plan.md) — уровни 1 и начало уровня 2.  
**Код:** `backend/migrations/000001` … `000006`, сервисы в `internal/service`, API под `/api/v1`.

Этот документ фиксирует **первый этап разработки**: что было заложено до появления CRM, привычек и гибкой RBAC, чтобы через год не вспоминать «как мы вообще начинали».

---

## 1. Карта бизнес-контекстов (как в проекте, а не абстрактная ERP)

Здесь не «идеальная» таблица из учебника, а **фактическое разделение** по модулям репозитория.

| Контекст | Ответственность | Границы (что не делает) |
|----------|-----------------|-------------------------|
| **Identity & Access** | Пользователь (`users`), пароль, глобальная роль `ADMIN` / `USER`, JWT, сессии | Не знает про сделки и привычки; workspace-роли изначально в `user_workspaces`, позже — расширенная модель в отдельных миграциях |
| **Workspace (тенант)** | Организация: `workspaces`, членство `user_workspaces`, настройки «текущего» workspace в `user_preferences` | Не реализует бизнес-логику модулей |
| **Module platform** | Справочник `modules`, подключение к workspace `workspace_modules`, лицензии `user_module_licenses`, триггеры при создании workspace | Не содержит доменных сущностей CRM/Habits |
| **Habits** | Привычки, журнал, история (миграции `000007+`) | Не управляет контактами CRM |
| **CRM** | Контакты, компании, сделки, воронки (миграции `000016+`) | Не подменяет биллинг (его как отдельного контекста в этой базе пока нет) |
| **Projects / Tasks / Notes** | Сущности с `workspace_id` | Изолируются по workspace, не смешивают данные между тенантами |

**Зачем это в репозитории:** новые фичи и промпты к AI должны явно попадать в контекст («это CRM» / «это workspace»), а не тянуть SQL из соседнего модуля без `workspace_id`.

## 2. Архитектурные решения (ADR) — первый набор

Шаблон из [plan.md](./plan.md); ниже — решения, которые **уже зафиксированы кодом и миграциями**.

### ADR-P1-001: Модульный монолит на Go

- **Контекст:** одна деплойная единица, общая БД, быстрая итерация.
- **Решение:** монолит (`cmd/api`), слои handler → service → repository, DI в `internal/di`.
- **Последствия:** (+) простые транзакции и отладка; (−) нужна дисциплина не импортировать «чужие» сервисы напрямую там, где нужен контракт.

### ADR-P1-002: Мультитенантность через `workspace`, не через «tenant_id» в каждом пользователе

- **Контекст:** один пользователь может состоять в нескольких организациях.
- **Решение:** сущность **`workspaces`** + связь **`user_workspaces`** (`UNIQUE(user_id, workspace_id)`). Данные продуктовых модулей висят на **`workspace_id`**.
- **Последствия:** (+) естественная модель B2B; (−) каждый запрос к бизнес-данным обязан знать workspace (в URL или из контекста).

### ADR-P1-003: PostgreSQL, первичные ключи UUID

- **Решение:** `gen_random_uuid()` для доменных id, кроме служебных таблиц вроде `request_logs` (serial).
- **Последствия:** (+) безопасные идентификаторы без координации; (−) чуть больше размер индексов, чем у bigint.

### ADR-P1-004: Миграции `golang-migrate`, нумерация `0000xx_`

- **Решение:** SQL в `backend/migrations`, строгий порядок; up/down для отката.
- **Последствия:** история схемы воспроизводима; нельзя «тихо» править уже применённые up без новой миграции.

### ADR-P1-005: Модули ERP как строки в БД + включение на workspace

- **Решение:** таблицы `modules`, `workspace_modules`; при **INSERT** в `workspaces` триггер подключает core-модули и триал опциональных (`000006`).
- **Последствия:** (+) включение фич без передеплоя кода; (−) логика «что включено» размазана между SQL-триггером и приложением (нужно помнить оба слоя).

### ADR-P1-006: Две «оси» ролей (заложено с первых миграций)

- **Глобально:** `users.role` — `ADMIN` / `USER` (системные функции, не workspace).
- **В workspace:** поле `user_workspaces.role` (строка, позже дополнено отдельной системой ролей и Casbin в других частях документации).

Подробнее: `backend/docs/SYSTEM/ROLES_GLOBAL_VS_WORKSPACE.md`.

## 3. Мультитенантность: поток данных и правила

1. **Тенант** = строка в `workspaces` (`id` UUID).
2. **Доступ пользователя к тенанту** = строка в `user_workspaces`.
3. **Владелец** workspace хранится в `workspaces.owner_id` (ссылка на `users`) — отдельно от членства; типично owner также есть в `user_workspaces`.
4. **Изоляция данных:** все последующие доменные таблицы (habits, crm, …) содержат **`workspace_id NOT NULL REFERENCES workspaces(id)`** и индексы с префиксом `workspace_id`.
5. **HTTP:** маршруты вида `/api/v1/workspaces/:workspaceId/...` + middleware проверки членства (реализация в приложении, не в этой миграции).

**Инвариант:** бизнес-операция не должна читать/писать строки без фильтра по `workspace_id`, если только это не глобальный админ-флоу (и тот оговаривается отдельно в коде).

## 4. Миграции 000001–000006: что именно создаётся

Порядок важен: каждая следующая может ссылаться на предыдущие.

| Файл | Назначение |
|------|------------|
| `000001_infra_request_logs` | Таблица `request_logs` — технический журнал (serial id, без tenant). |
| `000002_auth_users` | `users`: email, password hash, `role` (глобальная), статус, профиль. |
| `000003_core_workspaces` | `workspaces` + триггер `update_updated_at` (функция `update_updated_at_column`). |
| `000004_core_user_workspaces` | Связь пользователь ↔ workspace, поле `role` для роли участника. |
| `000005_auth_user_preferences` | `user_preferences`: один ряд на пользователя, `current_workspace_id` (удобство UI). |
| `000006_modules_system` | `modules`, `workspace_modules`, `user_module_licenses`, seed модулей, триггер на автоподключение модулей к новому workspace. |

### Ключевые ограничения и связи

- `users.email` — **UNIQUE**.
- `user_workspaces` — **UNIQUE(user_id, workspace_id)**.
- `workspace_modules` — **UNIQUE(workspace_id, module_id)**.
- `user_module_licenses` — частичные уникальные индексы под `scope` `all_workspaces` vs `single_workspace` + CHECK на согласованность `workspace_id`.

## 5. Инварианты и бизнес-смысл (этап 1)

| Инвариант | Где закреплено | Смысл |
|-----------|----------------|--------|
| Пользователь с уникальным email | `000002` | Один аккаунт на адрес. |
| Workspace всегда имеет владельца | `workspaces.owner_id NOT NULL` | Юридически/продуктово «кто создал» зафиксирован. |
| Один пользователь — одна запись предпочтений | `user_preferences.user_id UNIQUE` | Точка хранения «последнего выбранного workspace». |
| Код модуля глобально уникален | `modules.code UNIQUE` | Стабильный идентификатор для API и фронта. |
| Новый workspace получает core-модули автоматически | Триггер `tr_workspace_enable_modules` | Не забыть включить habits/crm/projects/tasks вручную. |

## 6. Что сознательно не входит в «часть 1»

Чтобы не смешивать этапы:

- Гранулярные права, Casbin, `workspace_roles`, `permission_catalog` — отдельная волна (**миграция `000022` и документация в** `backend/docs/SYSTEM/`).
- Доменные таблицы CRM, Habits, Projects — **часть 2+** этого цикла (`part_2.md` и далее), но они **всегда** опираются на `workspace_id` из этой части.
- OpenAPI/детальные сценарии каждого эндпоинта — уровень 2 плана, можно вынести рядом с `part_2.md`.

## 7. Воспроизведение фундамента с нуля (чек-лист)

1. Поднять PostgreSQL, создать БД и пользователя.
2. Выставить переменные окружения (DSN) как в проекте.
3. Выполнить миграции до `000006` включительно: `migrate -path migrations -database "$DSN" up` (или эквивалент из Makefile/README проекта).
4. Проверить: после ручного `INSERT` в `users` и `workspaces` срабатывает триггер модулей — в `workspace_modules` появляются строки для core-модулей.
5. Убедиться, что приложение поднимается и отдаёт health/auth без ошибок подключения к схеме.

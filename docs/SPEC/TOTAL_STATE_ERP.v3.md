## 1. Общая концепция системы

### 1.1. Назначение
Корпоративная система управления (ERP) с модульной архитектурой, построенная на принципах мультитенантности и масштабируемости. Каждый модуль может быть включён/отключён независимо, что позволяет гибко настраивать систему под потребности конкретного бизнеса.

### 1.2. Ключевые принципы
- **Мультитенантность** – все данные изолированы по `workspace_id`
- **Модульность** – система состоит из независимых модулей, каждый со своей БД и API
- **Core-модули** – всегда включены (workspace, users, auth)
- **Опциональные модули** – подключаются по лицензии (CRM, Projects, Habits и т.д.)
- **Гранулярные права** – доступ к каждому действию настраивается индивидуально
- **Двухуровневая ролевая модель** – глобальные роли и роли внутри workspace

### 1.3. Базовая терминология

| Термин | Определение |
|--------|-------------|
| **Workspace** | Рабочее пространство компании-клиента. Все данные изолированы. |
| **Пользователь** | Физическое лицо, имеющее доступ к системе. Может состоять в нескольких workspace. |
| **Глобальная роль** | Роль во всём приложении (`users.role`): `ADMIN` (бог приложения) или `USER` (обычный пользователь). |
| **Системная роль workspace** | Статус участника в workspace (`user_workspaces.role`): `OWNER` (владелец), `ADMIN` (директор), `MEMBER` (сотрудник), `GUEST` (гость). |
| **Кастомная роль** | Должность/функция, создаваемая ADMIN-ом workspace (например, "Менеджер по продажам"). Назначается MEMBER-ам. |
| **Право (Permission)** | Конкретное действие вида `{модуль}:{сущность}:{действие}` (например, `crm:deal:create`). |
| **Модуль** | Самостоятельный функциональный блок (CRM, Projects, Habits и т.д.). |
| **Лицензия** | Право на использование модуля (глобальное или для конкретного workspace). |

## 11. Права доступа и ролевая модель (НОВАЯ)

### 11.1. Двухуровневая модель

```
УРОВЕНЬ 1: Глобальный (всё приложение)
├── ADMIN - полный доступ к любым workspace, управление пользователями
└── USER - обычный пользователь, работает только в своих workspace

УРОВЕНЬ 2: Системные роли workspace (статус участника)
├── OWNER - владелец workspace (создатель)
├── ADMIN - администратор workspace (управляет настройками)
├── MEMBER - сотрудник (активный участник)
└── GUEST - гость (только просмотр)

УРОВЕНЬ 3: Кастомные роли (должности)
├── Создаются ADMIN-ом workspace
├── Назначаются только MEMBER-ам (GUEST не получают права на запись)
├── Могут наследовать друг друга
└── Состоят из набора прав (permissions)

УРОВЕНЬ 4: Права (permissions)
├── Формат: {модуль}:{сущность}:{действие}
├── Пример: crm:deal:create, crm:deal:read, crm:deal:delete
└── Являются "кирпичиками" для построения ролей
```

### 11.2. Что такое системные роли workspace

| Роль | Статус | Неотъемлемые права |
|------|--------|---------------------|
| **OWNER** | Владелец | Может удалить workspace, передать владение, всё что может ADMIN |
| **ADMIN** | Директор | Управляет пользователями, модулями, создаёт кастомные роли |
| **MEMBER** | Сотрудник | Может иметь кастомные роли (должности), активно работает |
| **GUEST** | Гость | Только просмотр (read-only), не может получать права на запись |

**Важно:** Системные роли имеют **неизменяемый базовый уровень**:
- GUEST **всегда** read-only (даже если ADMIN попытается дать write-права)
- MEMBER может получить любые права через кастомные роли
- ADMIN и OWNER имеют все права автоматически

### 11.3. Глобальный ADMIN vs ADMIN workspace

| Тип ADMIN | Где действует | Что может |
|-----------|---------------|-----------|
| **Глобальный ADMIN** (`users.role = 'ADMIN'`) | Всё приложение | Зайти в любой workspace, управлять пользователями, видеть всё |
| **ADMIN workspace** (`user_workspaces.role = 'ADMIN'`) | Конкретный workspace | Управлять настройками ЭТОГО workspace, создавать роли |

### 11.4. Кастомные роли (примеры)

| Кастомная роль | Кому назначается | Права |
|----------------|-------------------|-------|
| Менеджер по продажам | MEMBER | crm:deal:create, crm:deal:read, crm:deal:update, crm:contact:read |
| Старший менеджер | MEMBER | Наследует "Менеджер по продажам" + crm:deal:delete |
| Логист | MEMBER | inventory:item:read, inventory:item:update |
| Аудитор | GUEST | Только read-права на отчёты |

### 11.5. Схема проверки прав

```
[Запрос] → [AuthMiddleware] → [WorkspaceMiddleware] → [ModuleMiddleware] → [PermissionMiddleware] → [Хендлер]
    1. Извлекает       2. Извлекает          3. Проверяет          4. Проверяет
       user_id из        workspace_id из        модуль и              права через
       JWT               URL, проверяет         лицензию              Casbin + индивидуальные права
                         членство
```

### 11.6. Текущий статус реализации прав (backend)

- ✅ Схема БД: `permission_catalog`, `workspace_roles`, `user_role_assignments`, `user_permissions`, `role_inheritance`
- ✅ Миграции данных: перенос из `user_workspaces` в `user_role_assignments`, триггеры системных ролей
- ✅ Инфраструктура Casbin: модель с доменами, адаптер, `casbin_rule`, загрузка/сохранение политик (graceful shutdown)
- ✅ PermissionService: CRUD ролей, назначения, индивидуальные права, эффективные права, наследование ролей, компенсирующие откаты
- ✅ API для прав: `/permissions/catalog`, `/roles`, `/roles/:roleId/inherit/:parentRoleId`, `/users/:userId/roles`, `/users/:userId/permissions`, `/me/permissions`
- ✅ Middleware-цепочка: Auth → Workspace → Module → Permission
- ✅ Боевой режим PermissionMiddleware: Casbin реально блокирует доступ (403) при отсутствии прав
- ✅ Индивидуальные права в runtime-проверке: при отказе по ролям PermissionMiddleware дополнительно проверяет `user_permissions` (формат `module:entity:action`) и при совпадении разрешает доступ
- ⚠️ Кэширование прав: нет TTL-кэша для `GetEffectivePermissions` (можно добавить на следующем этапе)

### 11.7. Новые таблицы для прав доступа

| Таблица | Назначение |
|---------|------------|

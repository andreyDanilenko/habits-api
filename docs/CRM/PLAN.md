## РЕЗЮМЕ: ПЛАН РАЗРАБОТКИ И СИСТЕМНЫЙ АНАЛИЗ ПРОЕКТА

### 1. Общий план разработки (этапы и статусы)

| Этап | Название | Статус | Ключевые результаты |
|------|----------|--------|----------------------|
| **Этап 1** | Ядро CRM | ✅ **Завершён** | Контакты, компании, сделки, воронки продаж. Полноценный CRUD, списки, карточки, связи. |

### 2. Архитектурные принципы (обеспечение масштабируемости)

Система строится как модульный SaaS с возможностью горизонтального масштабирования и разделения на микросервисы в будущем. Основные принципы:

- **Мультитенантность через Row Level Security (RLS)**  
  Все таблицы содержат `workspace_id`. RLS автоматически фильтрует данные по текущему workspace (переменная сессии). Это исключает утечки данных между клиентами и избавляет от необходимости писать `WHERE workspace_id = …` в каждом запросе вручную.

- **Мягкие связи между модулями**  
  Модули не используют внешние ключи (FOREIGN KEY) друг на друга. Вместо этого применяются отдельные таблицы связей (например, `project_entities` для проектов, позже `task_links` для задач). Это позволяет:
  - Хранить ссылки на сущности других модулей без жёсткой привязки.
  - Выносить модули в отдельные базы данных или микросервисы без нарушения целостности.
  - Обеспечивать независимость разработки и версионирования модулей.

- **Общее ядро (Core)**  
  Выделены сквозные сущности, которые всегда находятся в едином ядре:  
  - `workspaces` (рабочие пространства)  
  - `users` (пользователи)  
  - `projects` (проекты) – как общий контекст для группировки данных любых модулей.  
  Все остальные модули (CRM, Habits, Tasks и т.д.) ссылаются на ядро через мягкие связи или через `project_id`, но не имеют прямых зависимостей друг от друга.

- **Событийная модель (Event Driven) – перспектива**  
  В дальнейшем межмодульное взаимодействие будет строиться на событиях (например, закрытие сделки в CRM порождает событие, на которое подписывается модуль задач для автоматического создания задачи). Это обеспечит максимальную слабую связанность.

### 3. Текущий этап: Модуль PROJECTS (функциональные требования)

#### 3.1. Сущности и их назначение

- **Проект** (`projects`) – контейнер для группировки любых сущностей системы (контактов, компаний, сделок, привычек, позже – задач).  
  Поля: название, описание, даты создания/обновления, привязка к workspace.

- **Связь проекта с сущностью** (`project_entities`) – запись о том, что некоторая сущность (с указанием типа и её ID) принадлежит проекту.  
  Поля: `project_id`, `entity_type`, `entity_id`.  
  Одна сущность может быть в нескольких проектах.

#### 3.2. Функциональные требования к интерфейсу (User Stories)

**Управление проектами:**
- Пользователь видит список всех проектов в своём workspace, отсортированный по дате последнего обновления.
- В списке каждый проект отображается с названием, кратким описанием (если есть), датой обновления и счётчиками количества привязанных сущностей по типам (контакты, компании, сделки, привычки).
- Доступны действия: создать проект, редактировать название/описание, удалить проект (с подтверждением, при удалении стираются только связи, сами сущности остаются).
- Поиск проектов по названию (с debounce).

**Детальная страница проекта:**
- Отображает название, описание, мета-информацию (дата создания, обновления).
- Вкладки для каждого типа сущностей: «Контакты», «Компании», «Сделки», «Привычки» (и в будущем «Задачи»).
- В каждой вкладке – список соответствующих сущностей, привязанных к проекту. Элементы списка кликабельны (переход в карточку сущности в соответствующем модуле).
- Для каждой сущности есть возможность удалить её из проекта (кнопка/иконка с подтверждением).
- Кнопка «Добавить» на вкладке открывает модальное окно для выбора сущностей данного типа, ещё не входящих в проект. В окне: поиск, чекбоксы для множественного выбора, счётчик выбранных, кнопка «Добавить».

**Интеграция с CRM:**
- В карточках контакта, компании, сделки добавляется новая вкладка «Проекты».
- Вкладка отображает список проектов, в которых участвует данная сущность, с возможностью перехода в проект и удаления из проекта.
- Кнопка «Добавить в проект» открывает модальное окно с выбором проектов (аналогично добавлению сущностей в проект, но наоборот – выбор проектов для сущности).

**Интеграция с модулем Habits (если присутствует):**
- В карточке привычки добавляется блок «Проекты» с аналогичным функционалом (просмотр, добавление, удаление).
- В общем списке привычек появляется фильтр по проектам (выпадающий список), позволяющий отобразить привычки, принадлежащие выбранному проекту, или «без проекта».

#### 3.3. Ограничения и особенности
- Сущность может быть одновременно в нескольких проектах.
- При удалении проекта связи удаляются каскадно, но сами сущности остаются в системе.
- Все операции проверяют права доступа: владелец workspace и администраторы имеют полный доступ, участники могут добавлять/удалять сущности в проектах, гости – только просмотр.

### 4. Критерии готовности этапа PROJECTS

- [ ] Реализован интерфейс списка проектов (CRUD, поиск).
- [ ] Реализована детальная страница проекта с вкладками по типам сущностей.
- [ ] Работает добавление сущностей в проект (через модальное окно).
- [ ] Работает удаление сущностей из проекта.
- [ ] В CRM-карточках (контакт, компания, сделка) присутствует вкладка «Проекты» с корректным отображением и возможностью добавления/удаления.
- [ ] (Опционально) В модуле Habits реализована интеграция (блок проектов в карточке и фильтр в списке).
- [ ] Все интерфейсы имеют состояния загрузки, ошибок и пустые состояния.
- [ ] Соответствие принципам мягких связей (нет прямых FK на модули, только через `project_entities`).
- [ ] Проекты корректно изолированы по workspace (RLS).

---

### 5. Будущие этапы (кратко)

- **Этап 4 (Tasks):** создание независимого модуля задач с собственными таблицами и API. Задачи будут иметь поле `project_id` (мягкая ссылка) для привязки к проектам. Интеграция с CRM через таблицу связей `task_links` (аналогично `project_entities`). Отдельный интерфейс «Мои задачи», виджеты в проектах.
- **Этап 5 (Коммуникации и автоматизация):** подключение внешних сервисов (email, мессенджеры, телефония), построение отчётов, настройка триггеров. Все новые модули будут следовать тем же принципам мягких связей и опираться на общее ядро (workspace, users, projects).

---

Данный план и спецификация обеспечивают **масштабируемость, модульность и возможность поэтапного ввода функциональности** без необходимости переписывать ядро системы. Все решения соответствуют современным практикам построения SaaS-платформ.

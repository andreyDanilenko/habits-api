Как сделать, чтобы бренд и тема “держались” при выходе и зависели от домена/воркспейса
1) Бренд (лого + название) должен жить в workspace, а не в localStorage и не в пользователе
В БД уже есть поля workspaces.logo_path и workspaces.logo_scale — это и есть “источник истины”.
Front при загрузке приложения должен получать текущий workspace с бэкенда (GET /api/v1/workspaces/current) и уже из ответа рендерить:
workspace.name
workspace.logoUrl
workspace.logoScale
Тогда при logout ничего “ломаться” не будет: после выхода ты возвращаешься на страницу, но домен всё равно укажет нужный воркспейс (см. пункт про домены), и UI снова подтянет его бренд.
2) Theme (темизация) должна быть исключительно от workspace, а не пользователя (по умолчанию)
Чтобы “руководитель навязал тему участникам”, нужно сделать политику приоритета:
Добавь в модель воркспейса настройку политики темы, например:
workspace.theme_policy = 'LOCKED_BY_WORKSPACE' | 'USER_CAN_OVERRIDE'
При применении темы фронт/бэк должны выбирать источник так:
если LOCKED_BY_WORKSPACE: применять тему из workspace всегда
если USER_CAN_OVERRIDE: применять тему пользователя только если он её менял (иначе — дефолт воркспейса)
Важно: если хотите полностью независимость от localStorage, то пользовательские темы тоже должны храниться на бэке (см. следующий пункт).
3) Если нужна “независимость от localStorage” — храните тему участника в БД, а localStorage только как кэш
Варианты (лучший для твоей задачи — БД):
Базовый вариант “тема только воркспейс”
не хранить тему пользователя вообще
фронт всегда применяет только workspace.theme_config
Вариант “тема воркспейса, но при USER_CAN_OVERRIDE участник может иметь свою”
создать таблицу, например user_workspace_preferences:
user_id
workspace_id
theme_override_config (json)
is_theme_override_enabled (boolean)
при загрузке воркспейса сервер возвращает:
workspace.theme_config
workspace.theme_policy
и если USER_CAN_OVERRIDE — user_override (если есть)
Тогда даже если пользователь вышел/зашёл с другого устройства — тема будет такой же, потому что она в БД.
4) Домены: домен -> воркспейс -> бренд и тема
Да, “наверно нужно делать по домену”. Это самый правильный путь для тиенантов.
Добавь таблицу соответствия:
domains(domain TEXT UNIQUE, workspace_id UUID, is_active BOOL)
В backend middleware/логике workspaces/current:
брать Host (или X-Forwarded-Host если proxy)
находить workspace_id по domain
применять HasAccess (для авторизованных пользователей)
для неавторизованных:
можно просто вернуть воркспейс (или только бренд/публичные настройки)
Тогда “после logout” ты снова входишь на те же страницы под тем же доменом, и:
сервер определяет нужный workspace
фронт рендерит его бренд
фронт применяет его тему
5) Что именно возвращать фронту из GET /workspaces/current
Чтобы фронту не пришлось “смешивать” источники:
Возвращай как минимум:
workspace.name
workspace.logoUrl/logoScale
workspace.theme_config
workspace.theme_policy
Если разрешён override пользователя — добавь:
user_theme_override (или null)
6) Как реализовать “навязать тему участнику”, но оставить шанс “не навязывать”
Интерфейс в workspace settings (владельцу/админам) должен иметь переключатель:
“Тема воркспейса фиксирована (участникам нельзя менять)”
Тогда:
при LOCKED_BY_WORKSPACE игнорируй любые пользовательские настройки
при USER_CAN_OVERRIDE показывай участнику UI для выбора темы, но сохраняй в user_workspace_preferences
Мини-чеклист “что нужно сделать в архитектуре”
Добавить domains и выбирать workspace по Host.
Добавить theme_policy в workspaces.
Хранить бренд (logo_path, logo_scale) в workspaces (уже сделано).
Хранить тему воркспейса в workspaces (и отдавать в workspaces/current).
При необходимости хранения пользовательской темы — хранить override в БД на уровне user_id + workspace_id, а localStorage сделать только кэшем.
Если скажешь, какой вариант политики ты хочешь как “стандарт по умолчанию” (только locked или разрешать override членам), я предложу точную схему таблиц/эндпоинтов и приоритеты данных (что именно и в каком порядке сервер возвращает).
